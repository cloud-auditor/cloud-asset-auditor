# Topology diagrams

Two diagrams of the **Northwind** estate — the fictional company the built-in
demo provider models — generated by the auditor itself rather than drawn by
hand. Every box is an asset the tool collected and every arrow is a
relationship it inferred, labelled with the edge kind and, where several were
summarised into one, the count.

| File | Audience |
|---|---|
| `northwind-high-level.*` | The shape of the estate — one box per provider and resource type, and how the providers connect |
| `northwind-low-level.*` | Every asset and every edge, for tracing a specific path |

Each exists in three formats: `.excalidraw` (editable — open at
<https://excalidraw.com>), `.svg` (vector, prints cleanly), `.png` (drop into a
document).

## Provenance — read this before citing them

**These are synthetic.** Northwind is not a real company and none of these
addresses, zones, clusters or accounts belong to anybody. The fixture lives in
`internal/providers/demo/fixtures.go`.

That is deliberate. A topology diagram of a real estate is a complete map of
someone's infrastructure — private addresses, internal hostnames, account
identifiers, which subnet the database sits in. It is precisely the document an
attacker would want, and it does not belong in a public repository. So the
committed diagrams are generated from a fixture, and the tool is pointed at
real tenancies only on machines that own them, writing into the gitignored
`/.local/` directory.

The generation path is real, though, which is the point: the same command
against real credentials produces the same artefacts for your own estate.

## What the diagrams actually claim

An inferred graph makes two very different kinds of statement, and they are
drawn differently:

- **Solid edges are exact joins.** A Service selector matching Pod labels, an
  Ingress naming a backend, an OCID placing a subnet inside a VCN. These come
  from a document that names both ends.
- **Dashed edges are heuristic.** A DNS record whose value happens to equal a
  load balancer's address; a CNAME matching a mesh node's hostname. Cross-cloud
  joins have no authoritative document, so they are matched on address or name.
  A dashed edge is a strong hint, not a fact.
- **`traffic-allow` and `traffic-deny` are policy, not observed traffic.** They
  say a NetworkPolicy, Tailscale ACL or NetBird rule *permits* or *forbids* a
  flow — not that anything ever used it. Denials are drawn separately from
  grants on purpose: a denial rendered like a grant reads as reachability,
  which is the exact opposite of what the rule says.
- **Absence of an edge is not proof of isolation.** It can equally mean no
  collected relationship joins the two — a resolver that needed a raw payload
  the snapshot did not carry, or a provider that was skipped.

## Regenerating

```bash
just diagrams          # both diagrams, all three formats, from the demo fixture
```

Against a real estate, drop `--demo` and add your own scope:

```bash
auditor topology --detail medium --group-by provider -o d2 | d2 - out.svg
auditor topology -o excalidraw > out.excalidraw   # then edit at excalidraw.com
```

The renderers are deterministic — sorted nodes and edges, content-hashed
element ids — so regenerating an unchanged estate produces byte-identical
files, and a diff in these files means the estate actually changed.

Rendering `.svg`/`.png` needs [`d2`](https://d2lang.com) and `rsvg-convert`
(`brew install d2 librsvg`); the `.excalidraw` file needs neither.
